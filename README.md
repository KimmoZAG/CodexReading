# Codex 是个什么项目

> 一份给工程师看的 introduction，不是营销稿。读这份之前你最好已经写过几年代码、踩过 agent 的坑。

如果你在 2025 年之后用过任何"能改你代码"的 AI 工具，大概率见过 Codex 的影子。这个项目（`codex-rs`）是 OpenAI 把那套能力做成开源、能本地跑、能嵌进 IDE 的版本。仓库在 `github.com/openai/codex`。

我第一次翻它的时候，本以为会看到一个"调一下 API、拼拼 prompt"的脚本。结果打开 `codex-rs` 目录，200 来个 crate 铺面而来，瞬间有点懵。后来才搞清楚：它复杂，是因为它认真地在解决一个被很多人低估的问题——

**怎么让一个会自己写代码、自己跑命令的模型，在你机器上是安全的。**

## 它到底由什么组成

别被 crate 数量吓到。真正撑起整个系统的就几块：

- **`codex-core`**：智能体的大脑。会话、采样循环、工具调用、审批，全在这一个 crate 里（也是仓库里最大的一块，近 600 个文件）。
- **`codex-cli`**：你敲 `codex` 时跑的那个二进制。它很薄，主要管登录、解析参数、决定用哪种界面。
- **`codex-tui`**：终端里的界面，基于 ratatui。
- **`codex-app-server`**：把 core 包成一个 JSON-RPC 服务，IDE 和桌面端连的就是它。
- **`codex-exec-server`**：真正去执行 shell 命令的地方，而且跑在沙箱里。
- **`codex-protocol`**：上面所有这些组件之间说话用的"通用语言"（事件和指令的类型定义）。

剩下那一百多个 `codex-*` 基本是工具库、适配器和小组件，用到再查就行。

## 一个值得记住的设计决定

Codex 不是把所有逻辑塞进一个进程，而是按**信任边界**拆成了几个进程：CLI 起一个 app-server，core 在 app-server 里跑，需要真跑命令时再交给一个被沙箱裹着的 exec-server。

为什么这么绕？因为模型产出的指令不可信。让它直接在你本机 `system()` 掉一条它"觉得该跑"的命令，是灾难。Codex 的做法是：模型说"我要执行 X"，先过策略检查，危险的需要你点头，然后才在一个受限进程里跑。哪怕那个进程被注入了，它手里也没有你的 API key，能搞坏的范围也有限。

这套"假设模型会犯错，所以先用笼子关住它"的思路，贯穿了整个仓库。看懂这一点，后面读工具系统、沙箱、审批那几块就顺了。

## 怎么读这个仓库

我顺手做了一份由浅入深的导读（就在同仓库的 `site/` 目录，能直接部署成网页），建议这么读：

1. 先建立进程模型（cli / app-server / exec-server 怎么协作）；
2. 再钻 `codex-core` 的公共 API——其实就两个方法：`submit(Op)` 和 `next_event()`，一个发指令、一个收事件；
3. 然后看主循环 `run_turn`，它本质就是"问模型 → 它要么回一段话、要么要调个工具 → 执行工具、把结果塞回去再问"的循环；
4. 工具、沙箱、TUI、协议、配置，都是围着这个轴展开的。

正文里每个 `path:line` 标注都对应仓库里的真实位置，可以边读边跳过去看。

## 一些老实话

- 它**重**。想改核心行为，得先穿过不少"上下文压缩、skill 注入、hook 编排"之类的准备代码，真正的采样循环反而没那么长。这是生产级 agent 的常态，不是过度设计。
- 它的**配置即安全策略**。你在项目里写的那份 `codex.toml`（允许访问哪些目录、跑哪些命令），直接决定了沙箱的上限。
- 行号会随版本漂移，但 `run_turn`、`ApplyPatchHandler`、`dispatch_any_with_terminal_outcome` 这类名字很稳，靠名字搜比靠行号靠谱。

如果你只是想用，装好直接 `codex` 进交互，或 `codex exec "..."` 非交互跑一条任务。如果想改，上面的导读能省你不少在 `core/src` 深处迷路的时间。

祝读得顺。
